# ИКФ — доставка заявки модератору: очередь, восстановление и диагностика

## Контракт

- После успешного POST /submit PostgreSQL в **одной транзакции** переводит редакцию в \`SUBMITTED\` и создает outbox \`MODERATION_CARD\` с уникальным \`dedupe_key\`. HTTP-успех означает **принято сервером**, а не «модератор уже увидел».
- Фоновый worker переносит карточку, палитру (по возможности) и вложения в \`WRITERS_SUBMISSION_MOD_CHAT_ID\`. Итоговое \`DELIVERED\` означает, что Telegram Bot API подтвердил отправку всех обязательных частей комплекта в чат; прочтение и решение модератора **не подтверждаются**.
- Промежуточный прогресс каждого Telegram-сообщения сохраняется в поле \`delivery_progress_json\`. При рестарте worker может продолжить с сохраненной карточки и не пересылать уже отмеченные вложения. Отдельные экземпляры worker имеют уникальные lease ID; срок аренды по умолчанию 15 минут для больших комплектов.
- Важно: Telegram Bot API не предоставляет атомарной транзакции с PostgreSQL или идемпотентного \`sendMessage\`. Если процесс завершился **после фактической отправки Telegram, но до сохранения checkpoint в БД**, теоретически возможен дубликат. Обещать абсолютную exactly-once доставку нельзя. Комплект содержит UUID заявки для ручного выявления дублей.

## Статусы в Mini App

| Код | Что видит автор |
| --- | --- |
| QUEUED | В очереди отправки модератору |
| SENDING | Передаем комплект |
| RETRYING | Ошибка Telegram, автоматическая повторная попытка |
| DELAYED | Комплект ожидает дольше 5 минут |
| NEEDS_ATTENTION | Очередь требует действий администрации |
| DELIVERED | Комплект доставлен в чат Telegram (не означает прочтение) |

Клиент может нажать «Проверить доставку». Этапы доступны только владельцу собственной заявки через подписанную Telegram-сессию и фильтрацию по \`author_user_id\` в SQL. Не передаются внутренние chat ID, URL медиа, Telegram message ID и traceback. Неудачная проверка delivery-статуса не должна мешать просмотру черновика.

## Watchdog

Каждую минуту (не чаще) worker проверяет состояние outbox \`MODERATION_CARD\` на предмет \`PERMANENT_FAILED\` и старых (>300 секунд) невыполненных событий. Пишет \`WRITERS_MODERATION_DELIVERY_BACKLOG\` в журнал с количеством, состояниями и временем самой старой заявки, **без содержания работ**. Если задан \`owner_user_id\`, отправляет приватное уведомление владельцу с ограничением до одного уведомления в 15 минут. При недоступности Telegram отправка предупреждения может не получиться, но запись останется в серверном журнале.

## Команды владельца в личных сообщениях боту

- \`/writers_moderation\` — последние 20 доставок: UUID, состояние, число попыток, код ошибки. Сортировка приоритетно показывает проблемы.
- \`/writers_moderation_retry UUID\` — после устранения причины возвращает \`PERMANENT_FAILED\` или \`RETRYABLE_FAILED\` в очередь. \`DELIVERED\` не пересылает и подтвержденные checkpoint не стирает.
- Существующие \`/writers_delivery\` и \`/writers_retry\` относятся к **одобренным рекламным постам владельца**, а не к входящим заявкам, и продолжают работать отдельно.

## Развертывание и безопасный откат

- Миграция добавляет \`delivery_progress_json TEXT NOT NULL DEFAULT '{}'\` через \`ALTER TABLE ... ADD COLUMN IF NOT EXISTS\`. Ни один существующий outbox, черновик или файл не удаляется.
- Никаких новых ENV. Уже используется \`owner_user_id\` из действующего конфига. Не очищать PostgreSQL и \`DATA_DIR\`.
- **Не выпускать** без успешного CI (Python, Node и PostgreSQL) и проверки на реальных iOS/Android Telegram Mini App.
- Smoke: отправить заявку с двумя вложениями; временно смоделировать ошибку Telegram на втором файле; убедиться, что первый файл и карточка не дублируются после retry; проверить переход \`QUEUED → RETRYING → DELIVERED\` и кнопку статуса; убедиться, что статус другой учетной записи недоступен.
- Проверить отказ бота в доступе к чату модерации и уведомление владельцу при permanent failure. Затем восстановить права и вручную переотправить соответствующий UUID.
- При откате к старой версии необязательное новое поле в БД не используется; старый worker продолжает работу с исходным outbox. Не удалять новые столбцы: они сохраняют данные восстановлений.
