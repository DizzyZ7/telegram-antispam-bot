# 🛡️ telegram-antispam-bot

**telegram-antispam-bot** — Telegram-бот с антиспам-защитой, модерацией, статистикой, Lexicon и отдельным развлекательным слоем для разрешенных чатов.

## 🧩 Механика защиты

Challenge-Response слой работает по принципу Zero Trust v2:

1. **Intercept** — перехват нового участника в защищенном чате.
2. **Quarantine** — временное ограничение отправки контента до проверки.
3. **Challenge** — отдельная арифметическая проверка для точного `chat_id + user_id` с TTL.
4. **Verification** — корректный ответ сначала фиксируется в PostgreSQL как `verified`, затем Telegram возвращает права и только после успеха сессия становится `passed`.
5. **Re-verification** — повторное вступление в тот же или другой защищенный чат всегда создает новую независимую сессию; старый `passed` не является вечным whitelist.

Все проверки Zero Trust v2 с момента его включения сохраняются в PostgreSQL и переживают рестарты. Старые `passed_users` до v2 жили только в RAM и после прежних пересборок уже были потеряны, поэтому бот не создает фиктивную legacy-историю.

## ⚙️ Базовая конфигурация

Основные переменные окружения:

- `BOT_TOKEN` — Telegram Bot API token.
- `ALLOWED_CHATS` — allowlist только для legacy-функций вроде сводок/статистики. Он **не управляет Zero Trust** и не может отключить проверку входа в другом защищенном чате.
- `ZERO_TRUST_CHAT_IDS` — отдельный security allowlist. По умолчанию: `-1002619489118,-1003237014529,-1003643412493,-1003687304800`.
- `ZERO_TRUST_CHALLENGE_TTL_SECONDS` — TTL одной captcha-сессии, по умолчанию `300` секунд.
- `DATABASE_URL` — PostgreSQL DSN. Обязателен, пока `ZERO_TRUST_CHAT_IDS` содержит хотя бы один чат; при отсутствии/ошибке БД startup завершается fail-closed до polling.
- `SUMMARY_STORAGE_PATH` — SQLite-файл legacy-сводки.
- `SUMMARY_TIMEZONE` — таймзона сводки, по умолчанию `Europe/Moscow`.
- `DATA_DIR` — каталог постоянных runtime-данных. Для хостинга его нужно направлять в persistent storage.

Подробнее о security-state machine и rollout: [`docs/zero-trust-v2.md`](docs/zero-trust-v2.md).

### Zero Trust v2

Security scope намеренно отделен от остальных функций:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
ZERO_TRUST_CHAT_IDS=-1002619489118,-1003237014529,-1003643412493,-1003687304800
ZERO_TRUST_CHALLENGE_TTL_SECONDS=300
```

Капча идентифицирует конкретную сессию через `challenge_id`, поэтому старая кнопка не может решить более новую проверку того же человека. Один пользователь может одновременно иметь независимые challenge в разных чатах. При выходе незавершенная сессия отменяется; при новом входе создается новая.

Если Telegram временно не смог вернуть права после корректного ответа, сессия остается `verified`, а не ложно становится `passed`: ту же проверку можно повторить после восстановления Telegram API. При ошибке PostgreSQL бот не выдает доступ автоматически.

## 🧠 Дневная сводка и статистика

- `/summary` или `/today` — ручная сводка дня.
- `/stats` — статистика сообщений, стикеров, эмодзи и реакций.

Автоматическая отправка итогов дня не используется: сводка вызывается вручную.

## 🎭 Entertainment Autonomy v2

Entertainment включается только для явного allowlist. В текущем production-конфиге чат `-1002619489118` добавляется как default, при этом значение можно переопределить через environment:

```env
ENTERTAINMENT_CHAT_IDS=-1002619489118
```

Память разделяется по `chat_id + topic_id`: разные темы forum-чата не смешивают локальный контекст. Между разными чатами данные также не смешиваются.

Текущая версия поддерживает:

- локальное обучение на подходящих сообщениях;
- topic-aware генерацию текста;
- отдельную память и настройки чатов;
- `/fun` и `/fun_generate`;
- три режима поведения: `Спокойный`, `Живой`, `Активный`;
- определение фазы разговора (`quiet`, `warming_up`, `active`, `peak`, `cooldown`) по активности конкретной темы;
- restart-safe историю автономных действий в БД;
- anti-spam бюджеты на 30 минут и минимальные интервалы между действиями;
- запрет обычной автономной реплики в `peak`, чтобы бот не перебивал живой разговор;
- novelty/no-copy фильтр против точного или слишком близкого повторения памяти и собственных недавних ответов;
- один bounded supervisor-task на весь Entertainment вместо task-per-message;
- admin enable/disable и очистку памяти текущей темы;
- PostgreSQL и SQLite через единый storage contract;
- безопасную миграцию существующей V1 SQLite-памяти в PostgreSQL.

### Culture Memory Phase A

Entertainment хранит канонический хронологический поток культуры темы, а не только плоский список длинных текстовых сообщений. Поддерживаемые человеческие события:

- обычный текст;
- короткий текст и emoji-only сообщения;
- стикеры;
- фотографии;
- Telegram animation/GIF.

Для каждого события сохраняются доступные `chat_id`, `topic_id`, `message_id`, автор, время, reply-связь и подходящие metadata. Для стикеров/фото/animation сохраняются Telegram `file_id`/`file_unique_id` и metadata, но бинарные медиа-файлы постоянно не скачиваются и не складируются.

Старые текстовые строки при старте один раз backfill-ятся в Culture Memory через idempotent migration marker. Исходная legacy-таблица пока остается как rollback-источник. Генератор читает текстовую проекцию уже из канонической Culture Memory, а activity/autonomy budgets остаются на прежней text-only семантике — одни стикеры или emoji не заставляют бота отвечать чаще.

Пользователь управляет собственной памятью в текущем чате:

- `/fun_ignore_me` — не запоминать новые сообщения пользователя;
- `/fun_remember_me` — снова разрешить запоминание новых сообщений;
- `/fun_delete_me` — удалить из памяти бота уже сохраненные события этого пользователя во всем текущем чате, не удаляя сами сообщения Telegram.

Админская `/fun_forget` очищает только текущую тему и удаляет как Culture Memory, так и compatibility-текст этой темы. Другие темы и чаты не затрагиваются.

Панель `/fun` показывает отдельные счетчики текста, emoji, стикеров, фото и анимаций.

### Culture Memory Phase B

Текстовая генерация использует не только набор отдельных фраз, но и **хронологию разговора** внутри конкретной темы:

- события объединяются в разговорные серии с разрывом примерно до 8 минут;
- последовательные сообщения одного автора могут использоваться как единая split-фраза — полезно для Telegram-манеры писать мысль несколькими сообщениями подряд;
- сообщения разных авторов не склеиваются в один сырой текст, но переход `реплика → ответ` увеличивает вес естественного продолжения;
- явный Telegram reply имеет больший вес, чем простое соседство сообщений;
- если reply-цель уже удалена или выпала из retention, генерация безопасно продолжает работать по обычной хронологии.

Для старой истории не выполняется полный scan всех ~100000 событий. На одну генерацию движок берет свежий bounded-контекст до `ENTERTAINMENT_GENERATION_SAMPLE_LIMIT` и дополнительно детерминированно выбирает **4 последовательных исторических окна по 16 событий**. Это позволяет старым локальным мемам возвращаться в речь, но свежий разговор имеет больший вес, чем архив.

Emoji тоже стали частью культуры темы. Движок запоминает, рядом с какими словами люди использовали emoji, и может необязательно добавить к новой текстовой реплике до двух подходящих emoji. Недавно использованные ботом emoji-подписи подавляются, если есть локальная альтернатива. Emoji из другой темы/чата не участвуют.

Phase B не меняет частоту автономных ответов и не вводит новые фоновые задачи. Phase C использует тот же bounded Culture snapshot и те же autonomy budgets для безопасного контекстного переиспользования уже сохраненных Telegram media.

### Culture Memory Phase C

Phase C расширяет Culture Memory до локальной культуры команд, других Telegram-ботов и контекстного media reuse без увеличения частоты автономных действий.

Bootstrap learning работает так:

- человеческие команды вроде `/spawn`, `/spawn boss` и `/spawn@OtherBot boss` сохраняются в канонической памяти, но **не считаются человеческой активностью**;
- сообщения и поддерживаемые media других ботов тоже могут сохраняться как культура темы, но не увеличивают `human_messages_since`, не ускоряют autonomy и сами по себе не запускают ответ;
- сообщения самого Entertainment-бота отбрасываются до записи, поэтому self-learning loop невозможен;
- после `ENTERTAINMENT_BOOTSTRAP_TEXT_EVENT_THRESHOLD` (по умолчанию `10000` событий `TEXT + EMOJI` в конкретной теме) влияние команд и источников других ботов уменьшается, но сами события не удаляются из памяти;
- threshold и вся генерация остаются строго локальными для `chat_id + topic_id`.

Media reuse использует только уже сохраненные Telegram identifiers:

- стикеры, фото и animation/GIF отправляются повторно по `file_id`; бинарники бот постоянно не хранит;
- forwarded media никогда не выбирается для автономного reuse;
- кандидат должен совпадать с текущим контекстом; минимальный relevance для фото строже, чем для animation и стикеров;
- одинаковый `file_unique_id` не переиспользуется в одной теме чаще `ENTERTAINMENT_MEDIA_REPEAT_COOLDOWN_SECONDS` (по умолчанию `21600`, то есть 6 часов);
- два обычных non-direct `MEMORY_CALLBACK` подряд не отправляются;
- в `peak` media может реализовать только уже разрешенный direct action;
- ошибка Telegram при отправке устаревшего/невалидного `file_id` не записывается как успешный media callback: движок может один раз выполнить текстовый fallback того же разрешенного action slot.

Media **не имеет отдельного бюджета**. Сначала существующий Autonomy v2 решает, разрешено ли одно действие с учетом `Спокойный`/`Живой`/`Активный`, cooldown и активности людей. Только после этого уже разрешенный slot может быть реализован как подходящее media либо как текст. Поэтому Phase C не повышает максимальную частоту участия бота.

Приватность человека сохраняется для всех новых human events, включая команды и media:

- `/fun_ignore_me` — не запоминать новые события пользователя;
- `/fun_remember_me` — снова разрешить запоминание;
- `/fun_delete_me` — удалить уже сохраненную память этого пользователя в текущем чате.

Настройки Phase C:

```env
ENTERTAINMENT_BOOTSTRAP_TEXT_EVENT_THRESHOLD=10000
ENTERTAINMENT_MEDIA_REPEAT_COOLDOWN_SECONDS=21600
```

### Долгосрочная память

Старая граница `5000` больше не используется. По умолчанию Entertainment держит около `100000` канонических событий на каждую тему форума. Для одной текстовой генерации читается только bounded-проекция до `1500` свежих событий плюс небольшие исторические окна, поэтому большая история не загружается целиком в каждый запрос.

Retention настраивается через ENV:

```env
ENTERTAINMENT_MEMORY_LIMIT=100000
ENTERTAINMENT_GENERATION_SAMPLE_LIMIT=1500
ENTERTAINMENT_MEMORY_PRUNE_BUFFER=1000
```

Очистка выполняется пакетно: тема может временно вырасти до `MEMORY_LIMIT + PRUNE_BUFFER`, после чего старый хвост удаляется одним batch и остается `MEMORY_LIMIT` самых свежих событий. Это заметно снижает нагрузку по сравнению с тяжелым `DELETE` после каждого нового сообщения.

### Режимы поведения

Пользователь больше не настраивает процент «лени» или ручную задержку. Движок сам решает, когда участие уместно:

- **🌙 Спокойный** — максимум 1 автономное действие за 30 минут, минимум 15 минут между действиями и минимум 8 человеческих сообщений после предыдущего действия.
- **✨ Живой** — максимум 2 действия за 30 минут, минимум 6 минут между действиями и минимум 4 человеческих сообщения.
- **⚡ Активный** — максимум 3 действия за 30 минут, минимум 3 минуты между действиями и минимум 2 человеческих сообщения.

Старые `/fun_laziness` и `/fun_cooldown` оставлены только как временные compatibility hints: они больше не меняют поведение Autonomy v2 и направляют администратора в `/fun`.

### PostgreSQL на Bothost

`runtime_env.py` загружает локальный `.env`, а `.gitignore` исключает реальные credentials. В репозитории хранится только безопасный шаблон `.env.example`.

Для **Zero Trust v2** PostgreSQL обязателен, пока `ZERO_TRUST_CHAT_IDS` не пуст. При отсутствии корректного `DATABASE_URL` production `main.py` завершает startup до polling, чтобы защита не могла молча отключиться.

Entertainment тоже использует PostgreSQL, когда `DATABASE_URL` задан с `postgres://` или `postgresql://`:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

Если Zero Trust явно отключен пустым `ZERO_TRUST_CHAT_IDS`, Entertainment по-прежнему умеет использовать `$DATA_DIR/entertainment.db` при отсутствии `DATABASE_URL`. Для production с защитой входа требуется PostgreSQL.

Реальную строку подключения не добавляйте в Git или исходный код — задайте ее как `DATABASE_URL` в environment проекта на Bothost либо в локальном `.env`, который не коммитится.

По умолчанию ошибка подключения к настроенному PostgreSQL останавливает запуск вместо молчаливого создания второй SQLite-базы. Это защищает и Zero Trust, и Entertainment от fail-open/split-brain состояния.

Аварийный Entertainment fallback можно включить только явно:

```env
ENTERTAINMENT_DB_FALLBACK_SQLITE=1
```

Он не является fallback для Zero Trust: security-layer остается fail-closed.

### Миграции памяти

При запуске с PostgreSQL бот сначала проверяет старый `$DATA_DIR/entertainment.db` и, если он существует, безопасно импортирует V1 данные. Затем для выбранного backend выполняется Culture Memory backfill существующего текстового хранилища.

Миграции:

1. не перетирают более новые настройки PostgreSQL;
2. сохраняют старые сообщения и исходные legacy ID;
3. используют migration markers, поэтому повторный запуск не создает дубли;
4. не удаляют автоматически исходную legacy-таблицу/SQLite-файл;
5. при ошибке останавливают startup вместо запуска с частично перенесенной памятью.

В логах запуска появляются `ZERO_TRUST_SECURITY_SCOPE`, `ZERO_TRUST_STORAGE_READY`, `ENTERTAINMENT_STORAGE_READY` и `ENTERTAINMENT_CULTURE_MEMORY_READY` с безопасными параметрами/счетчиками, но без credentials/DSN и без текста сообщений. После старта автономного цикла также появляется `ENTERTAINMENT_SUPERVISOR_READY`.

## 🛠 Установка и запуск

```bash
git clone https://github.com/DizzyZ7/telegram-antispam-bot.git
cd telegram-antispam-bot
pip install -r requirements.txt
python main.py
```

`main.py` — production entrypoint. `legacy_main.py` импортируется как compatibility-модуль, но его старые RAM captcha handlers отключаются до начала polling и не являются источником доверия Zero Trust v2.

Для чтения обычных сообщений группой Telegram бот должен действительно получать эти сообщения: обычно это обеспечивается правами администратора либо соответствующей настройкой Group Privacy Mode.
