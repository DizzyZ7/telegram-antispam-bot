# 🛡️ telegram-antispam-bot

**telegram-antispam-bot** — Telegram-бот с антиспам-защитой, модерацией, статистикой, Lexicon и отдельным развлекательным слоем для разрешенных чатов.

## 🧩 Механика защиты

Challenge-Response слой работает по принципу Zero Trust:

1. **Intercept** — перехват нового участника.
2. **Quarantine** — временное ограничение отправки контента.
3. **Challenge** — арифметическая проверка с TTL.
4. **Verification** — успешный пользователь получает права обратно, проваленная проверка завершается удалением/баном согласно текущей логике бота.

## ⚙️ Базовая конфигурация

Основные переменные окружения:

- `BOT_TOKEN` — Telegram Bot API token.
- `ALLOWED_CHATS` — список разрешенных ID чатов через запятую. Если переменная задана, она заменяет встроенный список legacy-чатов целиком; не указывайте один чат, если бот должен продолжать проверять вход в остальных ранее настроенных чатах.
- `SUMMARY_STORAGE_PATH` — SQLite-файл legacy-сводки.
- `SUMMARY_TIMEZONE` — таймзона сводки, по умолчанию `Europe/Moscow`.
- `DATA_DIR` — каталог постоянных runtime-данных. Для хостинга его нужно направлять в persistent storage.

## 🧠 Дневная сводка и статистика

- `/summary` или `/today` — ручная сводка дня.
- `/stats` — статистика сообщений, стикеров, эмодзи и реакций.

Автоматическая отправка итогов дня не используется: сводка вызывается вручную.

## 🎭 Entertainment Autonomy v2

Entertainment включается только для явного allowlist. В текущем production-конфиге чат `-1002619489118` добавляется как default, при этом значение можно переопределить через environment:

```env
ENTERTAINMENT_CHAT_IDS=-1002619489118
```

Память разделяется по `chat_id + topic_id`: разные темы forum-чата не смешивают локальный контекст. Между разными чатами данные также не смешиваются.

Текущая версия поддерживает:

- локальное обучение на подходящих сообщениях;
- topic-aware генерацию текста;
- отдельную память и настройки чатов;
- `/fun` и `/fun_generate`;
- три режима поведения: `Спокойный`, `Живой`, `Активный`;
- определение фазы разговора (`quiet`, `warming_up`, `active`, `peak`, `cooldown`) по активности конкретной темы;
- restart-safe историю автономных действий в БД;
- anti-spam бюджеты на 30 минут и минимальные интервалы между действиями;
- запрет обычной автономной реплики в `peak`, чтобы бот не перебивал живой разговор;
- novelty/no-copy фильтр против точного или слишком близкого повторения памяти и собственных недавних ответов;
- один bounded supervisor-task на весь Entertainment вместо task-per-message;
- admin enable/disable и очистку памяти текущей темы;
- PostgreSQL и SQLite через единый storage contract;
- безопасную миграцию существующей V1 SQLite-памяти в PostgreSQL.

### Culture Memory Phase A

Entertainment хранит канонический хронологический поток культуры темы, а не только плоский список длинных текстовых сообщений. Поддерживаемые человеческие события:

- обычный текст;
- короткий текст и emoji-only сообщения;
- стикеры;
- фотографии;
- Telegram animation/GIF.

Для каждого события сохраняются доступные `chat_id`, `topic_id`, `message_id`, автор, время, reply-связь и подходящие metadata. Для стикеров/фото/animation сохраняются Telegram `file_id`/`file_unique_id` и metadata, но бинарные медиа-файлы постоянно не скачиваются и не складируются.

Старые текстовые строки при старте один раз backfill-ятся в Culture Memory через idempotent migration marker. Исходная legacy-таблица пока остается как rollback-источник. Генератор читает текстовую проекцию уже из канонической Culture Memory, а activity/autonomy budgets в Phase A остаются на прежней text-only семантике — одни стикеры или emoji не заставляют бота отвечать чаще.

Пользователь управляет собственной памятью в текущем чате:

- `/fun_ignore_me` — не запоминать новые сообщения пользователя;
- `/fun_remember_me` — снова разрешить запоминание новых сообщений;
- `/fun_delete_me` — удалить из памяти бота уже сохраненные события этого пользователя во всем текущем чате, не удаляя сами сообщения Telegram.

Админская `/fun_forget` очищает только текущую тему и удаляет как Culture Memory, так и compatibility-текст этой темы. Другие темы и чаты не затрагиваются.

Панель `/fun` показывает отдельные счетчики текста, emoji, стикеров, фото и анимаций. Контекстное автономное переиспользование стикеров/фото и Meme Engine относятся к следующим фазам Culture Memory и в Phase A еще не включаются.

### Долгосрочная память

Старая граница `5000` больше не используется. По умолчанию Entertainment держит около `100000` канонических событий на каждую тему форума. Для одной текстовой генерации читается только bounded-проекция до `1500` подходящих текстовых источников, поэтому большая история не загружается целиком в каждый запрос.

Retention настраивается через ENV:

```env
ENTERTAINMENT_MEMORY_LIMIT=100000
ENTERTAINMENT_GENERATION_SAMPLE_LIMIT=1500
ENTERTAINMENT_MEMORY_PRUNE_BUFFER=1000
```

Очистка выполняется пакетно: тема может временно вырасти до `MEMORY_LIMIT + PRUNE_BUFFER`, после чего старый хвост удаляется одним batch и остается `MEMORY_LIMIT` самых свежих событий. Это заметно снижает нагрузку по сравнению с тяжелым `DELETE` после каждого нового сообщения.

### Режимы поведения

Пользователь больше не настраивает процент «лени» или ручную задержку. Движок сам решает, когда участие уместно:

- **🌙 Спокойный** — максимум 1 автономное действие за 30 минут, минимум 15 минут между действиями и минимум 8 человеческих сообщений после предыдущего действия.
- **✨ Живой** — максимум 2 действия за 30 минут, минимум 6 минут между действиями и минимум 4 человеческих сообщения.
- **⚡ Активный** — максимум 3 действия за 30 минут, минимум 3 минуты между действиями и минимум 2 человеческих сообщения.

Старые `/fun_laziness` и `/fun_cooldown` оставлены только как временные compatibility hints: они больше не меняют поведение Autonomy v2 и направляют администратора в `/fun`.

### PostgreSQL на Bothost

`runtime_env.py` загружает локальный `.env`, а `.gitignore` исключает реальные credentials. В репозитории хранится только безопасный шаблон `.env.example`.

Если `DATABASE_URL` отсутствует, Entertainment использует:

```text
$DATA_DIR/entertainment.db
```

Если `DATABASE_URL` задан с `postgres://` или `postgresql://`, PostgreSQL становится backend Entertainment:

```env
DATABASE_URL=postgresql://USER:PASSWORD@HOST:PORT/DATABASE
```

Реальную строку подключения не добавляйте в Git или исходный код — задайте ее как `DATABASE_URL` в environment проекта на Bothost либо в локальном `.env`, который не коммитится.

По умолчанию ошибка подключения к настроенному PostgreSQL останавливает запуск Entertainment вместо молчаливого создания второй SQLite-базы. Это защищает от split-brain памяти.

Аварийный fallback можно включить только явно:

```env
ENTERTAINMENT_DB_FALLBACK_SQLITE=1
```

Для production рекомендуется оставить fallback выключенным.

### Миграции памяти

При запуске с PostgreSQL бот сначала проверяет старый `$DATA_DIR/entertainment.db` и, если он существует, безопасно импортирует V1 данные. Затем для выбранного backend выполняется Culture Memory backfill существующего текстового хранилища.

Миграции:

1. не перетирают более новые настройки PostgreSQL;
2. сохраняют старые сообщения и исходные legacy ID;
3. используют migration markers, поэтому повторный запуск не создает дубли;
4. не удаляют автоматически исходную legacy-таблицу/SQLite-файл;
5. при ошибке останавливают startup вместо запуска с частично перенесенной памятью.

В логах запуска появляются `ENTERTAINMENT_STORAGE_READY` и `ENTERTAINMENT_CULTURE_MEMORY_READY` с безопасными счетчиками, но без credentials/DSN и без текста сообщений. После старта автономного цикла также появляется `ENTERTAINMENT_SUPERVISOR_READY`.

## 🛠 Установка и запуск

```bash
git clone https://github.com/DizzyZ7/telegram-antispam-bot.git
cd telegram-antispam-bot
pip install -r requirements.txt
python main.py
```

Для чтения обычных сообщений группой Telegram бот должен действительно получать эти сообщения: обычно это обеспечивается правами администратора либо соответствующей настройкой Group Privacy Mode.

## 🧪 Проверки

```bash
python -m compileall -q .
python -m unittest discover -s tests -p "test_*.py"
```

GitHub Actions дополнительно поднимает реальный PostgreSQL 17 и проверяет storage contract и Culture Memory отдельно от основного тестового job.
